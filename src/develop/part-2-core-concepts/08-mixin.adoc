== Mixin and Dynamics

_How a decorated method becomes a device command, with no command dictionary at all._

Module: `egse/mixin.py` (`cgse-core`)

Chapter 7 showed one way to turn a device command into a real method. A `CommandProtocol` builds a command dictionary from a YAML file, on the server side. `Proxy._add_commands()` (Chapter 6) then binds each dictionary entry as a real, callable method on the client. This chapter covers a second way to solve the same problem: a `Proxy` needs one method per device command, without a hand-written wrapper for each one. This second way builds no dictionary, reads no YAML file, and runs no load step at all.

Both mechanisms exist in the codebase today. Neither is a leftover from an earlier design, kept only until someone removes it. They are two different answers to two different situations, and most of this chapter explains why.

[NOTE]
.Python background: overriding `+__getattribute__+`
====
Python calls `+object.__getattribute__(obj, name)+` every time code reads `obj.name` — for a method call, a plain attribute, or a property. A class can override this method and intercept every such read. Both mixins in this chapter use that override to detect a decorated method and reroute it, rather than bind real methods once, up front. See the
https://docs.python.org/3/reference/datamodel.html#object.__getattribute__[Python data model docs]
for the full mechanism. Those docs also cover a recursion trap: this chapter's code avoids it with a direct call to `+object.__getattribute__+`.
====

=== Why a Mixin?

_One command, one method — with no hand-written duplication._

A device has, in practice, dozens of commands. A wrapper method per command, on both the `Controller` class and the `Proxy` class, creates a maintenance burden. Every command then exists as code in two places. A developer must keep the interface signature, the `Controller` implementation, and the `Proxy` forwarding logic in step by hand.

Chapter 6 already showed one fix for half of this problem: `@dynamic_interface`. A developer marks an interface method as dynamic. `Proxy._add_commands()` then binds it as a real method, at construction time. It uses the command dictionary the Control Server sends over.

That fix has a real cost. Chapter 6 already surfaced this cost, but never named it. `_add_commands()` runs only once: when the `Proxy` is constructed, and its first `send("send_commands")` request succeeds. If the Control Server is not running yet at that moment, the `Proxy` gets no commands at all. Every device method then stays an unimplemented stub. It raises `NotImplementedError` the moment a caller calls it. The only fix is to reconstruct the `Proxy`, or call `load_commands()` again by hand, once the server is actually up. For interactive or long-running client code, this is an awkward constraint: a developer must track startup order every time a `Proxy` gets constructed.

`egse/mixin.py` removes this constraint, for both sides of the connection. It defines two mixin classes: `DynamicCommandMixin`, on the `Controller`/device side, and `DynamicClientCommandMixin`, on the `Proxy`/client side. A *mixin*, here, is a class meant to be combined with another class through inheritance, not used on its own — it adds behavior, not a complete object. Neither mixin fetches or binds anything at construction time. Instead, each mixin overrides `+__getattribute__+` (see the callout above) and resolves a dynamically marked method lazily, on every single access. There is no "have the commands loaded yet?" state to track, because nothing is ever loaded ahead of time. A `DynamicProxy` can be constructed before its Control Server exists, sit idle, and work correctly the moment the server starts — with no reconnect step required.

=== The `dynamic_command()` Decorator

_One decorator, nine optional keywords, one wire command._

Where `@dynamic_interface` (Chapter 6) does one thing — stamp a bare `+__dynamic_interface+` marker onto a method — `dynamic_command()` does much more. It is a decorator *factory*. A caller supplies keyword arguments that describe how to build the on-the-wire command string, and how to process the response. The factory returns the actual decorator, which stamps a family of double-underscore-prefixed static attributes onto the interface method:

[source,python]
----
def dynamic_command(
    *,
    cmd_type: str,                       # required: "read", "write", "query", "transaction"
    cmd_string: str = None,
    cmd_string_func: Callable = None,
    process_response: Callable = None,
    process_cmd_string: Callable = None,
    process_kwargs: Callable = None,
    use_format: bool = False,
    pre_cmd: Callable = None,
    post_cmd: Callable = None,
    validate: Callable = None,
):
    ...
    def func_wrapper(func):
        setattr(func, "__dynamic_interface", True)
        setattr(func, COMMAND_TYPES[cmd_type], True)   # e.g. "__write_command"
        if cmd_string is not None:
            setattr(func, "__cmd_string", cmd_string)
        ...
        return func
    return func_wrapper
----

`+cmd_type+` is the only required argument. It must be one of `+"read"+`, `+"write"+`, `+"query"+`, or `+"transaction"+`. `COMMAND_TYPES` maps each value to a static attribute name (`+__write_command+`, `+__query_command+`, and so on) that tells the mixin how to dispatch the call. `+"read"+` is the odd case out: `+dynamic_command()+` requires a `+cmd_string+` (or `+cmd_string_func+`) only for `+"write"+`, `+"query"+`, and `+"transaction"+`. A pure `+"read"+` command never sends a command string to the device at all — it only polls, as the next section shows.

The `+cmd_string+` itself is a template, filled in from the decorated method's own arguments. Two styles are supported:

[source,python]
----
# string.Template style ($-substitution, the default)
cmd_string="CREATE:SENS:TEMP ${name} ${type} default=${default}"

# str.format style, opted into with use_format=True
cmd_string="CREATE:SENS:TEMP {name} {type} default={default:0.4f}"
use_format=True
----

Three keywords cover the rest of a command's lifecycle:

* `+process_cmd_string+` runs after the template is filled in — for example, to append a line terminator.
* `+process_response+` runs on the raw response, before it reaches the caller.
* `+pre_cmd+`/`+post_cmd+` run immediately before and after the transport call itself. `+pre_cmd+` receives the device transport, the function name, the built command string, and the original arguments; it must not return anything. `+post_cmd+` receives the transport and the response, and its return value *becomes* the response — so it can post-process or replace it.

Two further keywords round out the decorator. `+cmd_string_func+` is an escape hatch for a command string a template cannot express: a callable that builds the whole string itself, from the method's own arguments. `+validate+`, added most recently, names a callable that runs before anything else, with the same arguments as the decorated method; it raises `ValueError` on bad input and returns nothing otherwise. No device driver in the codebase uses `+validate+` yet, but the hook is live in `+handle_dynamic_command()+` (next section) as soon as one does.

=== `DynamicCommandMixin`: the Controller Side

_Every attribute read passes through one check first._

[source,python]
----
class DynamicCommandMixin:
    def __init__(self):
        if not hasattr(self, "transport"):
            raise AttributeError("Transport was not defined in sub-class of DynamicInterfaceMixin")

    def __getattribute__(self, item):
        attr = object.__getattribute__(self, item)
        if hasattr(attr, "__dynamic_interface"):
            attr = self.handle_dynamic_command(attr)
        return attr
----

This is the whole trick, and it rewards a slow read. Every attribute access on a `DynamicCommandMixin`-based object — not just a method call, *every* attribute access — passes through this `+__getattribute__+` override first. It fetches the attribute the normal way (`+object.__getattribute__+`, to avoid infinite recursion). Only if that attribute carries the `+__dynamic_interface+` marker does it get rerouted through `+handle_dynamic_command()+`. A subclass method that overrides the interface with a plain, undecorated implementation carries no marker, so it passes through untouched. This is the same rule Chapter 6 documented for `+@dynamic_interface+`: a subclass override always wins over dynamic dispatch. Here, the mechanism is `+__getattribute__+`, not a one-time binding loop.

The `+__init__+` check is a real, easy-to-trip-on ordering requirement, not a formality. `DynamicCommandMixin` assumes `self.transport` is already set by the time its own `+__init__+` runs. `self.transport` must be a `DeviceTransport`-shaped object that provides `+write+`, `+read+`, `+query+`, and `+trans+`. Python resolves `+super().__init__()+` calls through the method resolution order, so a `Controller` subclass must assign `self.transport` *before* it calls `+super().__init__()+`, not after. Reverse that order, and construction raises `AttributeError` immediately, from inside a mixin the subclass author might never read. The worked example below shows the correct order in real code.

`+handle_dynamic_command()+` does the actual work:

[source,python]
----
def handle_dynamic_command(self, attr):
    @functools.wraps(attr)
    def command_wrapper(*args, **kwargs):
        if hasattr(attr, "__validate"):
            attr.__validate(*args, **kwargs)

        if hasattr(attr, "__cmd_string"):
            cmd_str = self.create_command_string(attr, attr.__cmd_string, *args, **kwargs)
        elif hasattr(attr, "__cmd_string_func"):
            cmd_str = self.create_command_string(attr, attr.__cmd_string_func, *args, **kwargs)
        else:
            cmd_str = None

        with contextlib.suppress(AttributeError):
            attr.__pre_cmd(transport=self.transport, function_name=attr.__name__,
                            cmd_str=cmd_str, args=args, kwargs=kwargs)

        if hasattr(attr, "__write_command"):
            self.transport.write(cmd_str)
        elif hasattr(attr, "__read_command"):
            response = self.transport.read()
        elif hasattr(attr, "__query_command"):
            response = self.transport.query(cmd_str)
        elif hasattr(attr, "__transaction_command"):
            response = self.transport.trans(cmd_str)

        with contextlib.suppress(AttributeError):
            response = attr.__post_cmd(transport=self.transport, response=response)
        with contextlib.suppress(AttributeError):
            response = attr.__process_response(response=response)

        return response
    return command_wrapper
----

(Attribute access is written here with dot notation, for readability. The real source uses `+getattr(attr, "__cmd_string")+` and so on, since these names are not ordinary Python attributes.) Notice `+self.transport.read()+` takes no `+cmd_str+` argument. This is exactly why a `+"read"+` command needs no `+cmd_string+`: it is a pure polling read. Nothing is sent; something is only read back. `+pre_cmd+`, `+post_cmd+`, and `+process_response+` are each wrapped in `+contextlib.suppress(AttributeError)+`, rather than an `+if hasattr(...)+` check. This choice reads a little unusual: the "hook was not provided" case is handled as a caught exception, not a checked condition. It works identically either way, and it keeps all three optional-hook call sites visually uniform.

`+create_command_string()+`, the static method that fills in the template, does more than a single `+string.Template.substitute()+` call:

[source,python]
----
@staticmethod
def create_command_string(func, provider, *args, **kwargs) -> str:
    if callable(provider):
        cmd_string = provider(*args, **kwargs)
    else:
        process_kwargs = getattr(func, "__process_kwargs", expand_kwargs)
        template = string.Template(provider)
        sig = inspect.signature(func)
        bound = sig.bind(*args, **kwargs)
        variables = {...}   # bound.arguments, defaults filled in, **kwargs expanded via process_kwargs
        if hasattr(func, "__use_format"):
            cmd_string = provider.format(**variables)
        else:
            variables = {k: v.value if isinstance(v, enum.Enum) else v for k, v in variables.items()}
            cmd_string = template.safe_substitute(variables)

    if hasattr(func, "__process_cmd_string"):
        cmd_string = func.__process_cmd_string(cmd_string)
    return cmd_string
----

Three details matter here:

. It binds the call's `+*args, **kwargs+` against the *decorated method's own signature* (`+inspect.signature(func)+`). A template placeholder can therefore refer to a method parameter name directly, and fall back to that parameter's declared default when a caller omits it.
. An `+enum.Enum+` value is unwrapped to its `+.value+` automatically, before template substitution — but only on the template path, not the `+use_format+`/callable paths. This asymmetry is easy to miss; a command string built from an enum-typed argument can look wrong under `+use_format=True+` if a reader does not know it.
. `+process_cmd_string+`, if present, always runs last, no matter which of the three paths — template, `+.format()+`, or a callable provider — produced the string. It is the one post-processing hook every path shares.

=== `DynamicClientCommandMixin`: the Proxy Side

_No transport here — only a message to send._

The client-side mixin shares the exact same `+__getattribute__+` interception pattern as the Controller side: the same check for `+__dynamic_interface+`, the same lazy, per-access dispatch. Once it fires, `+handle_dynamic_command()+` does something different, because a `Proxy` has no local `self.transport` to talk to:

[source,python]
----
def handle_dynamic_command(self, attr):
    @functools.wraps(attr)
    def command_wrapper(*args, **kwargs):
        attr_name = attr.__name__
        try:
            inspect.signature(attr).bind(*args, **kwargs)
        except TypeError as exc:
            logger.error(f"Arguments do not match the signature of the function '{attr_name}': {exc}")
            return None

        device_method = get_function(self.__class__, attr_name)
        cmd = ClientServerCommand(
            name=attr_name,
            cmd=getattr(attr, "__cmd_string", ""),
            response=DynamicCommandProtocol.handle_device_method,
            device_method=device_method,
        )
        ce = CommandExecution(cmd, *args, **kwargs)
        return self.send(ce)

    command_wrapper.__signature__ = inspect.signature(attr)
    return command_wrapper
----

No command string is built here. The client only checks that the call's arguments *bind* against the interface method's signature. This catches an obviously wrong call before it leaves the process. On a mismatch, it logs an error and returns `None`; it does not raise.

When the arguments do bind, the wrapper builds a `ClientServerCommand`/`CommandExecution` pair (Chapter 7). This pair carries the command name, the raw `+cmd_string+` template, the call's arguments, and a reference to `+DynamicCommandProtocol.handle_device_method+`. The wrapper then hands the whole thing to `+self.send()+` — the same retry/reconnect machinery Chapter 6 already documented. The final line, `+command_wrapper.__signature__ = ...+`, copies the interface method's real signature onto the wrapper. This is why a tool like `help()` reports the real parameters, not a generic `+*args, **kwargs+`.

All the actual command-string construction happens on the *server* side, inside the Control Server's own `+DynamicCommandMixin.create_command_string()+` call. It uses the exact same `+__cmd_string+`/`+__process_cmd_string+`/etc. attributes. This only works because the interface class that carries those decorated methods is shared, unchanged, between the `Controller` and the `Proxy`. Both sides read the same markers off the same method; only what happens once a marked method is found differs.

=== A Worked Example: Old Style, New Style

_The same command, `homing()`, built two different ways._

The clearest way to see both systems side by side is not a hypothetical — it is two real hexapod drivers already in the codebase, for closely related hardware. Chapter 4's `factory//` example already introduced the PUNA/PUNA+ distinction as a `ControllerFactory` decision point; this is the code behind that decision.

`egse/hexapod/symetrie/alpha.py` and `puna.py` are the older style. `homing()` is a bare, undecorated stub on the interface:

[source,python]
----
# alpha.py
class AlphaControllerInterface:
    @dynamic_interface
    def homing(self):
        raise NotImplementedError

# puna.py
class PunaInterface(AlphaControllerInterface, DeviceInterface): ...
class PunaController(PunaInterface): ...            # no DynamicCommandMixin
class PunaProxy(Proxy, PunaInterface): ...           # plain Proxy, load_commands()
----

`egse/hexapod/symetrie/dynalpha.py` and `punaplus.py` are the newer style, for the PUNA+ variant of the same hexapod family. The same command, `homing()`, is now fully specified on the interface itself:

[source,python]
----
# dynalpha.py
class AlphaControllerInterface(DeviceInterface):
    @dynamic_command(cmd_type="transaction", cmd_string="c_cmd=C_HOME",
                      process_cmd_string=process_cmd_string, process_response=process_response)
    def homing(self):
        raise NotImplementedError

# punaplus.py
class PunaPlusInterface(AlphaPlusControllerInterface): ...

class PunaPlusController(PunaPlusInterface, DynamicCommandMixin):
    def __init__(self, hostname="127.0.0.1", port=23):
        self.transport = self.device = AlphaPlusTelnetInterface(hostname, port)   # <1>
        self.hostname = hostname
        self.port = port
        super().__init__()                                                        # <2>

class PunaPlusProxy(DynamicProxy, PunaPlusInterface):
    def __init__(self, device_id: str, *, timeout: float = PROXY_TIMEOUT):
        self._device_id = device_id
        super().__init__("", timeout=timeout, connect=False)

    def connect_cs(self):
        with RegistryClient() as reg:                                             # <3>
            service = reg.discover_service(self._device_id)
        ...
        self._endpoint = connect_address(protocol, service["host"], service["port"])
        super().connect_cs()
----
<1> `self.transport` is assigned *before* `+super().__init__()+` runs — exactly the order `+DynamicCommandMixin.__init__+` requires. Reverse the order, and construction raises `AttributeError`.
<2> This is the only line that actually invokes `+DynamicCommandMixin.__init__+`, through the method resolution order. Everything else `PunaPlusController` needs — `+is_connected+`, `+connect+`, `+disconnect+` — is a handful of ordinary, hand-written methods that delegate to `self.device`, because those are not device *commands* in the `+@dynamic_command+` sense.
<3> `PunaPlusProxy` overrides `+connect_cs+` — one of the `ControlServerConnectionInterface` methods from Chapter 6 — to resolve its Control Server's address from the Service Registry (Chapter 10) by `+device_id+`, instead of a fixed host and port from Settings, before it delegates to the inherited `+connect_cs()+` for the actual socket work. Command dispatch (this chapter) and connection-endpoint discovery (Chapter 10) stay cleanly separate here, composed rather than tangled together.

One detail is easy to mistake for a typo: `alpha.py` and `dynalpha.py` each define a class named `AlphaControllerInterface`. These are two distinct classes in two distinct modules, not the same class reopened. Python allows this because each module keeps its own namespace; nothing links the two beyond the shared name and the shared hardware they both describe.

The interface class stays small on both sides. `+PunaController+`/`+PunaProxy+` (old) and `+PunaPlusController+`/`+PunaPlusProxy+` (new) each define almost nothing themselves. Nearly the entire public command surface of a hexapod driver — `+homing+`, `+move_absolute+`, dozens of others — lives as decorated stubs on a shared interface class. Which mixin the `Controller`/`Proxy` pair inherits decides whether those stubs resolve through a one-time dictionary fetch (old) or lazy, per-access `+__getattribute__+` interception (new). The interface class itself does not need to know, or care, which system its `Controller`/`Proxy` pair ultimately uses.

=== One Interface, Both Decorators

_A device driver can mix the two systems on purpose._

The two systems are not a strict "old device, old decorator; new device, new decorator" split. A single interface class can use both, deliberately. ``egse/tempcontrol/keithley/daq6510.py``'s `DAQ6510Interface` decorates most of its methods with `+@dynamic_command+` — simple SCPI query or write commands that fit a template cleanly. A handful of methods — `+read_buffer+`, `+clear_buffer+`, `+create_buffer+`, `+configure_sensors+`, `+setup_measurements+`, `+perform_measurement+` — carry only the bare `+@dynamic_interface+` marker, with no `+cmd_string+` at all:

[source,python]
----
class DAQ6510Interface(DeviceInterface):
    @dynamic_interface
    def create_buffer(self, buffer_name: str, size: int) -> None:
        raise NotImplementedError

    @dynamic_command(cmd_type=CommandType.WRITE, cmd_string='TRACE:DELETE "${buffer_name}"')
    def delete_buffer(self, buffer_name: str) -> None:
        raise NotImplementedError

class DAQ6510Controller(DAQ6510Interface, DynamicCommandMixin):
    def create_buffer(self, buffer_name: str, size: int = 1000) -> None:
        ...   # a real, hand-written implementation — several transport calls, not one command string
----

`+create_buffer+` and its bare-`+@dynamic_interface+` siblings all need several distinct commands and some conditional logic against the device. One `+cmd_string+` template cannot express that. `DAQ6510Controller` provides an ordinary, hand-written override for every one of them. That override is a plain method, with no `+__dynamic_interface+` marker of its own, so `+DynamicCommandMixin.__getattribute__+` never intercepts it.

This is the same rule from earlier in this chapter — a subclass override always wins over dynamic dispatch — put to genuine use. `+@dynamic_interface+` alone serves only as a documentation and auto-completion stub here, its original purpose from Chapter 6, not as a request for dynamic dispatch. The class-level override is what makes that safe. `delete_buffer` and most of the rest are simple enough to template, so they use the richer decorator and need no hand-written body at all.

One small, confirmed inconsistency surfaced while this chapter was verified against the source. `CommandType`, the `str` enum some drivers use in place of a bare string for `+cmd_type+`, defines `+READ+`, `+WRITE+`, and `+TRANSACTION+` — but no `+QUERY+` member, even though `+"query"+` is a fully valid, commonly used `+cmd_type+` (`egse/hexapod/symetrie/dynalpha.py` uses `+cmd_type="query"+` throughout). A driver that wants a `+CommandType+`-typed query command has to fall back to the raw string instead. This is harmless — `+dynamic_command()+` validates against the string-keyed `COMMAND_TYPES` dict either way — but a five-minute fix; logged as *P-012*.

=== Where `DynamicProxy` Fits

_Two systems that coexist on purpose._

Chapter 6 flagged an open question, P-008. `Proxy` and `DynamicProxy` both build a dynamically commandable client object, through two apparently parallel mechanisms. Neither class carries a comment that explains why both exist. `egse/protocol.py` answers this directly, in a docstring that is easy to miss — it sits on the method that does the *least* work in one of the two subclasses:

[source,python]
----
class BaseCommandProtocol(DeviceConnectionObserver):
    def send_commands(self):
        """
        This method will be implemented by the subclass when the protocol needs to
        send the command definitions to the client. This is the case for the
        CommandProtocol where the commands are decorated with `@dynamic_interface`
        but not for the DynamicCommandProtocol where the commands are decorated
        with `@dynamic_command`.
        """
        ...
----

`CommandProtocol` (Chapter 7) overrides `+send_commands()+` to ship its `+self._commands+` dictionary to the client — the same dictionary `+Proxy._request_commands()+`/`+_add_commands()+` (Chapter 6) needs, to bind real methods at construction time. `DynamicCommandProtocol` leaves `+send_commands()+` as the inherited no-op, because there is no dictionary to ship. A `+@dynamic_command+`-decorated interface method already carries everything a `DynamicClientCommandMixin` client needs — the command name, the `+cmd_string+` template, the type — as static attributes on the method itself. Both the `Controller` and the `Proxy` see the same attributes, with no wire exchange required to get them there.

That is the resolution: `Proxy` + `CommandProtocol` + `+@dynamic_interface+` + a YAML command file is one complete, self-consistent system. `DynamicProxy` + `DynamicCommandProtocol` + `+@dynamic_command+` is a second, equally complete system, built to remove the "Control Server must already be running" requirement the first system carries. Neither is migration debt disguised as two systems. They are two different answers that coexist on purpose. Which one a device driver picks is a real design choice, not an accident of when the driver happened to be written. `egse/dummy.py` (Chapter 9's worked example) uses the first system end to end. The PUNA+ and DAQ6510 drivers above use the second. `daq6510.py` freely mixes bare `+@dynamic_interface+` stubs with `+@dynamic_command+`-decorated ones on the same interface class — which only makes sense once both systems' mechanics, not just their names, are understood.

P-008 originally flagged three separate issues. This chapter resolves only one: the *relationship* between `Proxy` and `DynamicProxy` is now documented, here. Both classes deserve a short cross-reference note that says the same thing, in the source itself, so the next reader does not need to find this chapter to get the same answer.

The other two items in that entry are unrelated `Proxy`-specific cleanup. Both stay open: the `# TODO (rik): remove all methods from Proxy that are also define in the BaseProxy` comment, and the `# FIXME: Check if this is still returning the proper port` in `+get_service_proxy()+`.

=== What Carries Forward

_Two threads left for later chapters._

Chapter 7 still owes a full treatment of `Command`, `CommandExecution`, and `ClientServerCommand.client_call()`/`+server_call()+`. This chapter used them only as much as needed, to show what `DynamicClientCommandMixin` hands to `+self.send()+`.

Chapter 9's `egse/dummy.py` worked example ties `control.py`, `proxy.py`, `command.py`, and `protocol.py` together end to end — but it exercises only the `+@dynamic_interface+`/`Proxy`/`CommandProtocol` half of this chapter. It predates `+@dynamic_command+` and was never migrated. A reader who wants the `DynamicProxy`/`DynamicCommandProtocol` half exercised end to end needs a real device driver, not `dummy.py`. The PUNA+ and DAQ6510 excerpts above are the closest thing to a canonical example the codebase currently offers.
