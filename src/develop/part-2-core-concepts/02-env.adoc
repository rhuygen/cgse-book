== Environments

_Where things live on disk, at this site._

This chapter is about environment variables, not Python virtual environments. It covers the environment of the running process.

=== Why this chapter follows Settings and Setup

Chapter 4 repeated one fact throughout: the location comes from `egse.env`. This covered the local settings path, the configuration data location, and the Setup files directory. This chapter is the other half. `egse/env.py` turns two mandatory environment variables, `PROJECT` and `SITE_ID`, into every other location CGSE needs. Both `Settings` and `Setup` depend on this module to find files on disk.

Chapter 4 answered one question: what kind of configuration is this? This chapter answers the next question: once we know the configuration, where does it physically live, on this machine, at this site, for this project?

'''

=== Four Test Sites, One Codebase, No Hardcoded Paths

CGSE runs at four test sites: CSL, SRON, IAS, and INTA. It also runs across several projects: PLATO, ARIEL, and CubeSpec. Three locations change per site: the data storage root, the configuration repository, and the log file location. None of these can be a `CONSTANT` in code, because the same code runs unmodified at every site.

Reading `os.environ` directly at each call site is not a solution either, for three reasons:

* Every call site would need to remember the exact variable name, including the `<PROJECT>_` prefix convention.
* No single place could validate that a location exists, warn when it does not, or supply a fallback when a more specific variable is not set.
* Test code that must simulate a different site or project would need to mutate `os.environ` directly, with no guarantee that other code had not already read a stale, cached value.

`egse/env.py` is the only place in the codebase that reads or writes these project and site variables in `os.environ`. Every other module calls a named function instead, for example `get_conf_data_location()`, not `os.environ["PLATO_CONF_DATA_LOCATION"]`. The module docstring states this rule directly: "Do not use the environment variables directly in your code."

'''

=== The Naming Convention

_Two mandatory variables, five derived ones._

[source,python]
----
MANDATORY_ENVIRONMENT_VARIABLES = ["PROJECT", "SITE_ID"]

KNOWN_PROJECT_ENVIRONMENT_VARIABLES = [
    "DATA_STORAGE_LOCATION",
    "CONF_DATA_LOCATION",
    "CONF_REPO_LOCATION",
    "LOG_FILE_LOCATION",
    "LOCAL_SETTINGS",
]
----

Only `PROJECT` and `SITE_ID` are bare variable names. Every other name is a suffix. The code prefixes it with whatever `PROJECT` currently resolves to: `PLATO_DATA_STORAGE_LOCATION`, `ARIEL_DATA_STORAGE_LOCATION`, and so on. This prefix convention lets the same source tree run for PLATO one day and for ARIEL the next, on the same machine. Only the environment variables change.

`KNOWN_PROJECT_ENVIRONMENT_VARIABLES` is a plain list, not a dict that maps a name to a getter function. This matters: `setup_env()` (Section 3) uses the list only to decide which variables to load into the internal cache at startup. The list does not generate the getter and setter functions below it. Each of the five variables still has its own hand-written `get_X`, `set_X`, and `get_X_env_name` trio (Section 4).

*Design decision — no generic factory.* A cleverer version of this module could generate all fifteen functions from the list, through a loop or a factory. The module does not do this, and the choice holds up. The five variables differ enough in fallback behavior (Section 4.2) that a generic factory would still need a special case per variable. Fifteen short, readable, greppable functions are also easier to step through in a debugger than one generic function parameterized five ways.

'''

=== `setup_env()` and the `_Env` cache

==== Run-once initialization via `@static_vars`

[source,python]
----
@static_vars(is_initialized=False)
def setup_env():
    global _env
    if setup_env.is_initialized:
        return
    ...
    setup_env.is_initialized = True
----

The module calls `setup_env()` at import time, without condition, right after the `_Env` and `NoValue` class definitions. Many modules import `egse.env`, and each import transitively triggers this same call again. The function must do its real work — reading `os.environ` and filling the cache — only once.

`@static_vars`, from `egse.decorators`, attaches `is_initialized` as an attribute of the function itself. This avoids a separate global guard variable at module scope. The guard state sits next to the function it guards, instead of floating separately.

This task might look like a job for `functools.lru_cache` on a zero-argument function, but `lru_cache` does not fit here. `setup_env()` must be re-runnable on demand, not only memoized once. `env_var()` (Section 8) resets `setup_env.is_initialized = False` and calls `setup_env()` again, to force a fresh read of `os.environ` after a temporary change. An outside caller cannot invalidate a cached function this cleanly. A plain attribute flag allows it.

==== Why mandatory variables warn instead of raising

[source,python]
----
for name in MANDATORY_ENVIRONMENT_VARIABLES:
    try:
        _env.set(name, os.environ[name])
    except KeyError:
        logger.warning(f"The environment variable {name} is not set. ...")
        _env.set(name, NoValue())
----

A missing `PROJECT` or `SITE_ID` at import time does not raise an error. The code logs a warning and stores a `NoValue()` sentinel instead. This choice is deliberate.

`import egse.env` runs in contexts where the environment is not yet fully configured. Examples:

* a fresh Python REPL, for interactive debugging,
* a unit test that sets up its own environment inside the test body, and
* a `--help` invocation of a CLI tool that needs no setup at all.

An error at import time would make `import egse.env` fail in every one of these legitimate cases. The module defers the error to the moment a caller actually asks for a value that depends on the missing variable. `_check_no_value()` (Section 4.1) raises the error at that point, because that is when a missing variable becomes a real problem, not only a hypothetical one.

==== The `_Env` Class as a Cache, Not a Re-Implementation of `os.environ`

[source,python]
----
class _Env:
    def __init__(self):
        self._env = {}

    def set(self, key, value):
        if value is None:
            if key in self._env:
                del self._env[key]
        else:
            self._env[key] = value

    def get(self, key) -> str:
        return self._env.get(key, NoValue())
----

`_Env` is a thin wrapper around a dict. Every public `get_X()` function in this module reads from `_env`, never from `os.environ` directly. Every public `set_X()` function writes to both `os.environ` and `_env`. This duplication is deliberate, for two reasons:

* A child process, for example a subprocess a Control Server starts, inherits `os.environ`. It does not inherit this module's private cache. If `set_conf_data_location()` updated only `_env`, a subprocess would never see the change.
* Reading from `_env` makes `NoValue()` possible as a distinct "never set" sentinel (Section 3.4). `os.environ.get(key)` returns plain `None` for "not set." That would collide with the `set_X(None)` convention for "clear this value on purpose," covered next.

==== `NoValue` as a Sentinel That Isn't `None`, on Purpose

[source,python]
----
class NoValue:
    def __eq__(self, other):
        if isinstance(other, NoValue):
            return True
        return False

    def __bool__(self):
        return False
----

Passing `None` to any `set_X()` function means "unset this variable." The convention is consistent: `set_data_storage_location(None)` deletes the environment variable. Because of this convention, `None` cannot also mean "this was never set" inside the cache.

A getter needs to tell two states apart: the caller cleared this value on purpose, or nobody has set it yet. Downstream, both states behave the same way — both mean "no value available." But if `_env.get()` returned plain `None` for both, `_check_no_value()` could not tell a real, meaningful `None` apart from an unset variable, and could not raise a clear error.

`NoValue` solves this with a distinct type. Two properties make it work:

* It is falsy. `+__bool__+` returns `False`, so a plain `if not value:` check still behaves as expected.
* It compares equal to any other `NoValue` instance, through `+__eq__+`. Code can write `value == NoValue()` without needing `_env` to return the exact same object every time.

`NoValue` is a small, single-purpose sentinel type, not a general-purpose null object. Section 6 covers a case where this narrow equality contract was misapplied.

'''

=== The get/set/env-name triads

==== The shape, using `DATA_STORAGE_LOCATION` as the model

[source,python]
----
def get_data_storage_location_env_name() -> str:
    project = _env.get("PROJECT")
    return f"{project}_DATA_STORAGE_LOCATION"


def set_data_storage_location(location: str | Path | None):
    env_name = get_data_storage_location_env_name()
    if location is None:
        if env_name in os.environ:
            del os.environ[env_name]
        _env.set("DATA_STORAGE_LOCATION", None)
        return
    if not Path(location).expanduser().exists():
        warnings.warn(f"The location you provided ... doesn't exist: {location}.")
    os.environ[env_name] = str(location)
    _env.set("DATA_STORAGE_LOCATION", str(location))


def get_data_storage_location(site_id: str = None) -> str:
    project = _env.get("PROJECT")
    _check_no_value("PROJECT", project)
    site_id = site_id or _env.get("SITE_ID")
    _check_no_value("SITE_ID", site_id)
    data_root = _env.get("DATA_STORAGE_LOCATION")
    _check_no_value("DATA_STORAGE_LOCATION", data_root)
    data_root = data_root.rstrip("/")
    return data_root if data_root.endswith(site_id) else f"{data_root}/{site_id}"
----

Every one of the five known variables follows this same three-function shape:

* `get_X_env_name()` builds the `<PROJECT>_X` string.
* `set_X()` checks that the location exists and warns through `warnings.warn` if it does not. It never fails hard, because a caller may legitimately set a location that does not exist yet — for example, before running `--mkdir` from the CLI.
* `get_X()` reads the value from `_env` and raises through `_check_no_value()` if the value is unavailable.

`get_log_file_location()`, `get_conf_data_location()`, and their setters follow this same shape, with a different suffix. This chapter does not walk through each one line by line.

One detail in `get_data_storage_location()` deserves attention. The function appends `site_id` to the configured root, without a warning, if the root does not already end with it.

*Design decision — the data storage location is site-specific by construction.* No call to `get_data_storage_location()` can return a path that is not scoped to a site, even if the environment variable holds a bare, shared root. This guards against a real mistake: a shared root, configured once and reused across two sites, would silently mix data from CSL and SRON in the same folder tree.

==== Fallback Chaining, Where Only One Location Is Really Mandatory

`get_conf_data_location()` and `get_log_file_location()` need no environment variable of their own. If `<PROJECT>_CONF_DATA_LOCATION` is not set, the function falls back to `get_data_storage_location() + "/conf"`. The log file location falls back to `+.../log+` the same way.

Only three variables are truly mandatory: `PROJECT`, `SITE_ID`, and `<PROJECT>_DATA_STORAGE_LOCATION`. Every other location has a sensible default, derived from these three.

This default chain is a real usability decision for anyone who sets up a new test site. Three environment variables give a working CGSE environment: `PROJECT`, `SITE_ID`, and `<PROJECT>_DATA_STORAGE_LOCATION`. A site only needs to set the other four explicitly to deviate from the convention. In practice, that deviation is normal: most sites keep the configuration repository outside the data storage tree entirely (see `<PROJECT>_CONF_REPO_LOCATION`, Section 5).

'''

=== `CONF_REPO_LOCATION` is different in kind, not just in name

`CONF_REPO_LOCATION` differs from the other four variables in kind, not only in name. It points at a git working copy, `~/git/{project}-conf` by the CLI's own `--doc` help text, not at a generic data folder. This is the repository where CGSE configuration data lives under version control.

`CONF_DATA_LOCATION` is different again: it is where `Setup` YAML files are actually read from, day to day. In practice, a site's `CONF_DATA_LOCATION` can simply be a path inside the `CONF_REPO_LOCATION` working copy. The repository holds the `Setup` files under version control; the data location is how code finds them. The two often overlap on disk.

`Setup.get_path_of_setup_file()` (Chapter 4, Section 3) branches on `has_conf_repo_location()`. If the function returns true, extra checks in `_check_conditions_for_get_path_of_setup_file()` verify that the repository folder and the site's `data/<site>/conf` subfolder both exist. If not, the code falls back to a simpler path, built from `get_conf_data_location()`.

This branch leads to the one function in this module that does not behave the way its name promises.

'''

=== A Real Bug in `has_conf_repo_location()`

_Caught by reading the code and checking it._

[source,python]
----
def has_conf_repo_location() -> bool:
    location = _env.get("CONF_REPO_LOCATION")
    return True if location in (None, NoValue) else False
----

Compare this to `get_conf_repo_location()`, twelve lines below it in the same file:

[source,python]
----
def get_conf_repo_location() -> str | None:
    location = _env.get("CONF_REPO_LOCATION")
    if location in (None, NoValue()):
        ...
----

Compare the two checks. `get_conf_repo_location()` checks membership against `NoValue()`, an instance. `has_conf_repo_location()` checks against `NoValue`, the class itself, with no parentheses.

`+NoValue.__eq__+` (Section 3.4) returns `True` only when compared against another `NoValue` instance, through `isinstance(other, NoValue)`. A class object is never an instance of itself, so `isinstance(NoValue, NoValue)` is `False`. Also, `_env.get()` never actually returns Python's `None` (Section 3.3): `_Env.set()` deletes the key entirely, rather than storing `None`.

Two cases follow:

* `CONF_REPO_LOCATION` unset: `location` is a `NoValue()` instance. `location in (None, NoValue)` is `False` for both members. The function returns `False`.
* `CONF_REPO_LOCATION` set to a real path: `location` is a string. `location in (None, NoValue)` is also `False`. The function still returns `False`.

I confirmed this by running the code, not only by reading it. A quick reading tempts you to assume it works for the common case:

----
--- not set ---
has_conf_repo_location(): False
--- set to /tmp/someconf ---
has_conf_repo_location(): False
----

`has_conf_repo_location()` returns `False` every time, whether or not the environment variable is set. The whole codebase calls it from exactly one place: `egse/setup.py::get_path_of_setup_file()`:

[source,python]
----
if not has_conf_repo_location():
    setup_location = Path(get_conf_data_location(site_id)).expanduser()
else:
    setup_location = _check_conditions_for_get_path_of_setup_file(site_id)
----

Because `has_conf_repo_location()` always returns `False`, `not has_conf_repo_location()` is always `True`. The `else` branch never runs. That branch is the one that validates the configuration repository — it checks that the repository exists and that it contains a `data/<site_id>/conf` folder, before code trusts it. This branch is dead code today, at every site, whether or not `<PROJECT>_CONF_REPO_LOCATION` is configured.

This bug has caused no visible failure so far. The branch that does run, based on `get_conf_data_location()`, has its own reasonable fallback (Section 4.2). But the extra validation in `_check_conditions_for_get_path_of_setup_file()` never protects anyone today. That function checks that the repository folder and the site subfolder both exist, and raises a clear `NotADirectoryError` that names the exact environment variable to fix.

This is the kind of bug this book exists to surface. It causes no crash and no test failure. The common path has looked correct for years, while a validation branch quietly never runs. This bug is logged as *P-003* in the Pitfalls appendix, with the fix (`NoValue` to `NoValue()`) and a note to add a regression test that checks `has_conf_repo_location()` toggles correctly. No such test exists today. That gap is why the bug survived.

'''

=== `load_dotenv()` as a Narrow, Deliberate Override

[source,python]
----
def load_dotenv():
    """
    - set `CGSE_DOTENV_DISABLED=true` to disable loading the `.env` file
    - the `.env` file is searched for relative to the current working directory,
      unlike the default, which searches from the script location.
    """
    if not bool_env("CGSE_DOTENV_DISABLED") and (dotenv_location := find_dotenv(usecwd=True)):
        logger.debug(f"Loading environment variables from {dotenv_location}.")
        _load_dotenv(dotenv_path=dotenv_location)
----

`load_dotenv()` makes two small, specific changes to the default behavior of the `python-dotenv` package. Both changes are stated in the docstring, not left implicit:

* *It searches from the current working directory (`usecwd=True`), not from the script's location.* CGSE test scripts and CLI tools run from many different working directories: a test campaign's own folder, a user's home directory, wherever a shell happens to be. The relevant `.env` file, if one exists, belongs to that working context. It does not sit next to wherever `egse/env.py` happens to be installed on disk.
* *It adds an explicit escape hatch, `CGSE_DOTENV_DISABLED`.* Automatic `.env` loading is convenient during interactive development. It is unwanted during an automated or CI test run, where the environment needs full control and no stray `.env` file should leak in a surprise value.

The docstring states one more rule, easy to break by accident: _"don't use `load_dotenv` in any modules, only in entrypoints and apps."_ The docstring does not explain why, but the reason follows directly from Section 3.1's initialize-once design. A call to `load_dotenv()` deep inside an unrelated library module would mutate environment variables as a side effect of an unrelated import. It might run after `setup_env()` has already cached its snapshot. That is exactly the hard-to-trace bug that "one designated place does initialization" is meant to prevent.

'''

=== `env_var()`, the Context Manager for Tests

[source,python]
----
@contextlib.contextmanager
def env_var(**kwargs: str | int | float | bool | None):
    saved_env = {}
    for k, v in kwargs.items():
        saved_env[k] = os.environ.get(k)
        if v is None:
            if k in os.environ:
                del os.environ[k]
        else:
            os.environ[k] = v

    setup_env.is_initialized = False
    setup_env()

    yield

    for k, v in saved_env.items():
        if v is None:
            if k in os.environ:
                del os.environ[k]
        else:
            os.environ[k] = v

    setup_env.is_initialized = False
    setup_env()
----

`env_var()` is the mechanism that makes `Settings` and `Setup` unit tests practical. `test_settings.py` uses it through `from egse.env import env_var`. On entry, it does three things:

* it overrides one or more environment variables temporarily,
* it re-runs `setup_env()`, so the `_env` cache reflects the override — this is exactly why Section 3.1 needed `setup_env()` to be forcibly re-runnable, not just idempotent, and
* it yields control to the test body.

On exit, it restores the previous values and re-syncs the cache again.

*A second, smaller pitfall.* `env_var()` should restore the environment even when the test body raises, since it is a `contextlib.contextmanager`. But the restoration code after `yield` runs inside no `try`/`finally` block. An exception raised inside `+with env_var(...):+` propagates before that restoration code runs. A test that fails an assertion inside the context manager leaves the overridden environment variables in place for whatever code runs next. This is a second pitfall in the same module as Section 6's bug, logged as *P-004*.

The docstring adds one more note: _"This context manager is different from the one in `egse.system` because of the CGSE environment changes."_ Take this note seriously if you see both context managers imported in the same file. The two are not interchangeable, and using the wrong one will not necessarily fail loudly.

'''

=== `print_env()` and the `main()` CLI

_Diagnostics, briefly._

`print_env()` is a small reporting function with no side effect. It prints the current value of every known location, wrapped in `warnings.catch_warnings()` with warnings suppressed. It exists to give a calm diagnostic printout, not to also raise every warning the getters would normally raise for an unset optional variable.

One place outside this module calls `print_env()`: `Setup._check_conditions_for_get_path_of_setup_file()`, which dumps this context just before it raises a `LookupError`. This is genuinely useful there. A confusing environment-variable error is easier to debug with a full printout of what is actually set.

`main()`, reachable through `python -m egse.env`, is a fuller version of the same idea, aimed at a person who sets up a new site. It offers:

* `--full`, for a verbose dump that includes `sys.path` and `PATH`,
* `--doc`, to print a human-readable explanation of each variable's purpose — the same explanation this chapter gives, written for a terminal instead of for a book, and
* `--mkdir`, to create missing directories, instead of only reporting them as missing.

The `check_env_dir` and `check_env_file` inner closures exist only to avoid repeating ``main()``'s rich-formatted validation logic four times inline: a relative-path warning, a does-not-exist warning, and a not-a-directory warning. This code is routine and needs no further comment.

One stray comment at the bottom of `main()` deserves a brief note, not a deep dive:

[source,python]
----
# Do we still use these environment variables?
#
# PLATO_WORKDIR
# PLATO_COMMON_EGSE_PATH - YES
----

This comment is a leftover question to self from an earlier cleanup, never resolved. It causes no harm, but it is logged as *P-005* anyway. A "do we still use X" comment left in shipped code is exactly the kind of open question a departing architect should resolve directly, rather than leave for whoever reads the code next.

=== What carries forward

The pattern from Chapter 4 holds here too. This module's "why" is almost entirely about two goals: keep project and site variability out of every call site, and make the one unavoidable piece of global mutable state, `os.environ`, safe to reason about, through a single cache with a real initialize-once lifecycle.

This chapter produced two real findings: ``has_conf_repo_location()``'s inverted, dead logic, and ``env_var()``'s missing `try`/`finally`. Both are exactly what "go deep on the tricky bits, verify rather than assume" is meant to catch. Both now sit in the Pitfalls appendix, with enough detail for a fix to be a quick, well-scoped pull request.
