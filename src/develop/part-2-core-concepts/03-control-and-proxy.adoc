== Control Servers and Proxies

_The client/server foundation._

=== Configuration at Runtime

_Why this chapter follows Settings, Setup, and env._

Chapters 4 and 5 covered what configuration exists and where it lives. This chapter covers what uses that configuration while the system runs.

Every device in a Setup runs through a *Control Server*. Examples are a hexapod, a temperature controller, and a power supply. The Control Server is a process that owns the physical connection to the device.

A test script or a GUI does not talk to the device directly. It talks to a *Proxy* object instead. The Proxy object looks, to the calling code, almost like the device itself.

`egse/control.py`, in `cgse-core`, defines `ControlServer`. Every device Control Server inherits from this one abstract base class.

`egse/proxy.py` defines `Proxy` and its related classes. `Proxy` is the client-side counterpart to `ControlServer`.

Together, these two files define the one architectural pattern that most of CGSE's runtime behavior builds on. Later chapters assume this chapter's vocabulary. This includes the device drivers, the GUI clients, and the *Storage Manager* and *Configuration Manager*, which are also `ControlServer` subclasses, as the next section explains.

This chapter covers `ControlServer` and `Proxy` before the newer `egse/registry` module, and that order is deliberate. Understanding the classic model first makes the Service Registry's value clear later. See this chapter's closing section for what comes next.

=== One Process, Many Clients

_Why every device gets exactly one Control Server._

A physical device in a test facility can safely talk to only one thing at a time. A GUI and a test script must not open a serial connection to the same hexapod independently. CGSE enforces a strict separation to prevent this:

* One long-running server process owns each device or service. It owns the actual connection — a serial port, an Ethernet socket, a GPIB link, or whatever the hardware needs. It is the only process that ever talks to the device directly.
* Any number of client processes can exist — test scripts, GUIs, monitoring dashboards. Each client talks to the server process over ZeroMQ. No client talks to the device directly.

This separation gives a shared test facility two things it needs. First, exclusivity: the device cannot be commanded from two places at once and become confused. Second, location transparency: a test script does not need to know whether the hexapod's Control Server runs on the same machine or across the lab network. The script only needs an endpoint string.

`ControlServer` is the shared machinery for the server side of this relationship. It is reused well beyond individual device drivers. The Storage Manager and the Configuration Manager — two of CGSE's own infrastructure services — are themselves `ControlServer` subclasses. The same request/reply, registration, and monitoring machinery that runs a hexapod Control Server also runs the service that decides where housekeeping data gets written. This reuse shows how central this one base class is.

=== Three Sockets

_Commanding, service, and monitoring — one socket each._

[source,python]
----
self.dev_ctrl_service_sock = self.zcontext.socket(zmq.REP)  # "how are you, what are your ports"
self.dev_ctrl_mon_sock = self.zcontext.socket(zmq.PUB)  # periodic status/HK broadcast
self.dev_ctrl_cmd_sock = self.zcontext.socket(zmq.REP)  # the actual device commands
----

`+ControlServer.__init__+` sets up three separate ZeroMQ sockets. Each socket uses a different pattern, because each one solves a different problem.

* `dev_ctrl_cmd_sock` *(REQ/REP)* carries the device commands themselves — `homing()`, `set_temperature()`, or whatever the device protocol defines. REQ/REP is a strict, synchronous request-then-reply pattern: only one command is in flight at a time. This matches the one-device-at-a-time rule from the previous section. The base class leaves this socket unbound. The class docstring states the reason directly: "the device protocol shall bind the socket in the subclass." Binding requires the commanding port, and only a concrete subclass knows that port, through the abstract method `get_commanding_port()`, covered below under "The Abstract Contract of Four Methods, One Theme."
* `dev_ctrl_service_sock` *(REQ/REP)* is a separate request/reply channel. It answers questions about the server itself, not the device: what is your monitoring port, are you alive (`Ping`), and other service-level questions. Keeping this socket separate from the command socket has two benefits. A client that asks "are you there?" never waits behind an in-flight device command. And a slow device command can never block the server from answering a basic liveness check.
* `dev_ctrl_mon_sock` *(PUB)* broadcasts periodic status and HK data. PUB fits this job because monitoring differs from commanding in shape. Any number of listeners — a GUI, a logging process, a second GUI opened for debugging — can subscribe without the server tracking who is listening. The server publishes once; every subscriber receives it. A REQ/REP socket would force the server to track a client list and iterate over it on every tick. PUB/SUB gives this fan-out for free, through ZeroMQ itself.

==== The Poller FIXME

_A self-flagged rough edge, worth reading in the source._

[source,python]
----
self.poller.register(self.dev_ctrl_mon_sock, zmq.POLLIN)  # FIXME: I think this should not be registered
----

This line stays in the source as-is. This section explains why it looks suspicious, rather than just repeating the FIXME comment.

`dev_ctrl_mon_sock` is a `PUB` socket. It only ever sends; it never receives. Registering it for `POLLIN` — readability — in the poller is very likely inert. ZeroMQ should not report a `PUB` socket as readable in any normal flow. So this line probably does nothing harmful, but also nothing useful.

The Pitfalls appendix flags this as *P-007*: "verify and remove if confirmed inert." This book does not fix it outright. Removing a poller registration from a Control Server that runs day and night needs a deliberate test and a real deployment window. It does not belong as a silent edit made while writing documentation.

=== The Single-Threaded `serve()` Loop

_One thread, one loop, not a thread per socket._

[source,python]
----
while True:
    self.signaling.process_pending_commands()
    socks = dict(self.poller.poll(50))  # timeout in milliseconds, do not block

    if self.dev_ctrl_cmd_sock in socks:
        self.device_protocol.execute()
    if self.dev_ctrl_service_sock in socks:
        self.service_protocol.execute()
    if self.event_subscription.socket in socks:
        self.event_subscription.handle_event()

    if time_in_ms() - last_time >= self.mon_delay:
        ...  # send monitoring status
    if time_in_ms() - last_time_hk >= self.hk_delay:
        ...  # collect + store + propagate housekeeping

    self.handle_scheduled_tasks()

    if self.interrupted or killer.term_signal_received:
        break
    if not self.device_protocol.is_alive():
        break
----

`serve()` runs on one thread, in one loop, polling with a short timeout. It does not spawn a thread per socket. This is the single most important design choice in the whole class, so this section states the trade-off directly.

* *What this design buys:* device state can change in exactly one place. No lock is needed around device access. Two threads can never race to send two ZeroMQ messages on the same socket at the same time — ZeroMQ sockets are not thread-safe to share. The server's behavior for one tick reads as one sequence: poll, handle whatever is ready, check the clocks, run scheduled tasks. A person can hold this sequence in their head and step through it in a debugger.
* *What this design costs:* the docstring for `schedule_task` warns about it directly: "the `callback` function is executed in the `serve()` event loop, it shall not block!" Because everything runs on one thread, one slow operation stalls every other concern of the server for the same duration. A device command that takes three seconds, or a scheduled task that blocks on network I/O, stops all other commands from being processed. It stops monitoring data from being published. It stops HK data from being collected. This is not a hidden gotcha — it is the direct, unavoidable cost of choosing a single thread over several. It is also the reason `schedule_task` exists at all, as an escape hatch described later in this section, instead of calling blocking code directly from `before_serve` or a subclass override.
* *The 50ms poll timeout* balances two needs: react quickly to a new event, and do not spin the CPU for no reason. The timeout is not configurable per instance — it is a literal `50` written into the `serve()` method. Every Control Server needs roughly the same response time, under 100 milliseconds to a new command, so one fixed value is a reasonable simplification. No Control Server built on this base class has needed a different value so far.

==== The Wall-Clock Timer FIXME

_Why `time_in_ms()` is the wrong clock for a long-running loop._

[source,python]
----
# FIXME: we shall use the time.perf_counter() here!

last_time = time_in_ms()
last_time_hk = time_in_ms()
----

The `mon_delay` and `hk_delay` checks shown above (`time_in_ms() - last_time >= self.mon_delay`) read the clock with `time_in_ms()`, from `egse.system`. This function returns wall-clock time (`time.time()`), not monotonic time. The docstring for `time_in_ms()` says so directly: "if you are looking for a high performance timer, you should really be using `perf_counter()` instead."

Wall-clock time can jump — an NTP correction or a manual clock change can cause this. A Control Server is exactly the kind of process expected to run unattended for weeks at a time, long enough to see a jump happen. A backward jump makes `time_in_ms() - last_time` go negative. This stalls the monitoring and HK cadence until the deficit is made up. A forward jump fires the check early.

This gets the same treatment as the poller FIXME described above. It is formalized as *P-009* in the Pitfalls appendix, not fixed while writing documentation. Switching to a `perf_counter()`-based elapsed-time calculation is small and self-contained. But this is a live scheduling loop in a process that runs unattended. It deserves a deliberate pull request with its own test, not a silent edit.

==== The Ctrl-C Policy

_Why `serve()` won't let Ctrl-C interrupt it._

[source,python]
----
except KeyboardInterrupt:
    self.logger.warning("Keyboard interrupt caught!")
    self.logger.warning(
        "The ControlServer can not be interrupted with CTRL-C, send a quit command to the server instead."
    )
    continue
----

This is a deliberate operational policy, not a missing feature. A Control Server owns a live connection to physical hardware.

A `KeyboardInterrupt` can unwind the Python stack at any point. If `serve()` allowed that, the interrupt could land in the middle of a device command. It could skip `after_serve()`. It could skip Storage Manager de-registration. It could leave the sockets and the device connection in an undefined state.

The `quit()` method and the `interrupted` flag prevent this. They let the loop reach its own `break` statement, at the top of the loop body, on its own terms. The loop then runs its cleanup sequence in order: unregister from the Storage Manager, run `after_serve()`, close every socket explicitly, deregister from the Service Registry, and terminate the ZeroMQ context. Only then does it exit.

`SIGTERM` is still honored, through `killer.term_signal_received` from `egse.system.SignalCatcher`. This policy does not ignore all signals. It blocks one specific thing: an interactive Ctrl-C interrupting the loop at an arbitrary instruction. An orchestrated shutdown signal can still be checked at a safe point in the loop.

==== `schedule_task` and `handle_scheduled_tasks`

_Explicit cooperative multitasking._

[source,python]
----
def schedule_task(self, callback: Callable, after: float = 0.0, when: Callable = None):
    ...
    self.scheduled_tasks.append({"task": callback, "name": name, "after": scheduled_time, "when": when})
----

`serve()` runs on a single thread, as the previous section explained. `schedule_task` is how a device protocol defers work to a later tick of the loop, instead of blocking the current one. The method's own documentation calls it a deadlock-avoidance mechanism: "this function is intended to be used in order to prevent a deadlock."

`handle_scheduled_tasks` processes the task list once per loop iteration. A task runs immediately once it is overdue and its condition is satisfied. Each task runs inside a `try`/`except` block, so one failing task cannot take down the server — it gets rescheduled instead. A task whose `after` time has not arrived, or whose `when` condition is not yet true, goes back on the list for the next check.

The method processes the list with an unusual pattern: it reverses the list, then pops from the end inside a `while` loop. This processes the tasks in their original order, while still allowing newly rescheduled tasks to be appended without disturbing the tasks still waiting in this pass. The pattern is routine once you see the trick.

=== The Four-Method Contract

_One theme: how to reach this server at all._

[source,python]
----
@abc.abstractmethod
def get_communication_protocol(self) -> str: ...
@abc.abstractmethod
def get_commanding_port(self) -> int: ...
@abc.abstractmethod
def get_service_port(self) -> int: ...
@abc.abstractmethod
def get_monitoring_port(self) -> int: ...
----

Every concrete Control Server must supply its protocol and its three ports. This abstract contract is small and deliberately narrow. `ControlServer` does not force a subclass to structure its device commanding in any particular way. It only forces the subclass to state, explicitly, how to reach this server at all.

This is where Chapter 4's `CONSTANT`/`Settings`/`Setup` framework earns its keep in practice. A concrete implementation — the PUNA hexapod Control Server, for example — typically implements these four methods as one-line returns of module-level names. Those names load once from `+Settings.load(...)+` at import time:

[source,python]
----
def get_commanding_port(self):
    return COMMANDING_PORT
----

A commanding port is a textbook `Settings` value, by Chapter 4's own rule of thumb. It is fixed per site or per deployment, not per test. Changing it means editing a YAML file, not the code.

=== The `can_operate_without_registry()` Hook

_When a missing Service Registry is fatal, and when it isn't._

[source,python]
----
def register_service(self, service_type: str) -> None:
    self._service_id = self.registry.register(
        name=self.service_name,
        host=get_host_ip() or "127.0.0.1",
        port=get_port_number(self.dev_ctrl_cmd_sock),
        service_type=self.service_type,
        metadata={"service_port": ..., "monitoring_port": ...},
    )
    if self._service_id:
        self.registry.start_heartbeat()
    elif self.can_operate_without_registry():
        self.logger.warning(f"Failed to register '{self.service_name}' ... Continuing because ...")
    else:
        raise ServiceRegistrationError(...)
----

[source,python]
----
def can_operate_without_registry(self) -> bool:
    """... The default is strict: registration is required. Subclasses with explicitly
    configured, externally known endpoints may override this policy hook."""
    return False
----

By default, a Control Server that cannot register itself with the Service Registry treats that failure as fatal — it raises `ServiceRegistrationError`. Look at how a concrete hexapod Control Server overrides this policy hook:

[source,python]
----
def can_operate_without_registry(self) -> bool:
    return bool(COMMANDING_PORT and SERVICE_PORT and MONITORING_PORT)
----

This override does not mean "always tolerate a missing registry." It means something narrower: tolerate a missing registry only when this server's ports are statically configured in Settings, rather than assigned dynamically by the operating system. A non-zero, explicitly set port counts as static; a `0` port, assigned by the OS, does not.

That condition is the whole point. If a device's ports are fixed, well-known values from a YAML file, a client can in principle be told the endpoint directly, and connect without ever asking the registry. Losing the registry degrades that server; it does not break it.

A server that relies on OS-assigned ports has no such fallback. Without the registry, nobody can discover which port it ended up on. For that server, a failed registration really is fatal.

`can_operate_without_registry()` is a policy hook, in the Template Method style. The right answer depends on a fact only the concrete subclass knows: whether its ports are static or dynamic. `ControlServer` supplies the mechanism — what to do with the answer — without hardcoding the policy — what the answer should be.

=== `is_control_server_active()`

_A raw, low-level ping, separate from the Proxy._

[source,python]
----
def is_control_server_active(endpoint: str = None, timeout: float = 0.5) -> bool:
    ctx = zmq.Context.instance()
    socket = ctx.socket(zmq.REQ)
    socket.connect(endpoint)
    socket.send(pickle.dumps("Ping"))
    rlist, _, _ = zmq.select([socket], [], [], timeout=timeout)
    if socket in rlist:
        response = pickle.loads(socket.recv())
        return_code = response == "Pong"
    socket.close(linger=0)
    return return_code
----

This module-level function duplicates, in miniature, what `Proxy.ping()` does — described later in this chapter, under "`BaseProxy` and `Proxy`, the Client Side." It opens a `REQ` socket, sends `"Ping"`, and expects `"Pong"` back within a timeout.

The function stands alone, separate from any `Proxy` instance. This lets code that only wants to check whether something is listening at an endpoint skip building a full `Proxy` object. A full `Proxy` object, as that later section explains, tries to load its entire command set as soon as it is constructed.

`is_control_server_active()` is a liveness check with no side effects. It opens a short-lived, disposable socket. This suits, for example, a startup script that probes several endpoints in sequence before deciding what to launch.

=== Two Independent Hierarchies

_Why `ControlServer` is not a `Proxy`, and what's shared instead._

`ControlServer` and `Proxy`/`BaseProxy` do not share a common base class. They are two independent class hierarchies. What they share is a wire protocol: pickled Python objects sent over a ZeroMQ `REQ`/`REP` socket, with the literal strings `"Ping"` and `"Pong"` as the handshake.

What is shared in code is a vocabulary: `get_commanding_port`, `get_service_port`, and `get_monitoring_port`. Both sides need to agree on what a "commanding port" means. But the server's job — own the socket, bind it, serve requests, own the device — differs enough in shape from the client's job — connect, send, wait for a reply, degrade gracefully on timeout. Forcing both into one hierarchy would not help.

=== `BaseProxy` and `Proxy`

_The client side, in three sequential classes._

==== Three Responsibilities, Three Classes

_Connection, transport, and dynamic commands — one class each._

[source,python]
----
class ControlServerConnectionInterface:      # the connect/disconnect/reconnect contract
class BaseProxy(ControlServerConnectionInterface):   # the actual ZeroMQ REQ socket + send()/ping()
class Proxy(BaseProxy, ControlServerConnectionInterface):  # + dynamic command loading
----

`ControlServerConnectionInterface` defines its connection-lifecycle methods as `@dynamic_interface` stubs. Each stub raises `NotImplementedError`. This is the same marker mechanism used elsewhere in device protocol classes — the `DynamicProxy` section below explains why it matters there too. The marker reserves a method name for connection management. A dynamically loaded device command of the same name must not silently overwrite it. The class docstring states this directly: the interface "guarantees that connection commands do not interfere with the commands defined in the `DeviceConnectionInterface`," which is loaded from the Control Server.

`BaseProxy` implements the actual socket handling. `Proxy` adds one more mechanism on top: the ability to grow new methods at runtime, one per command the connected Control Server actually offers. The `load_commands()` section below covers this. It is the single most distinctive thing about this class.

==== `send()`, Retry, and Reconnect

_What "connected" means in ZeroMQ._

[source,python]
----
def send(self, data, retries=REQUEST_RETRIES, timeout=None):
    ...
    if self._socket.closed:
        self.reconnect_cs()
    self._socket.send(pickle_string)
    while True:
        socks = dict(self._poller.poll(timeout_ms))
        if self._socket in socks and socks[self._socket] == zmq.POLLIN:
            return pickle.loads(self._socket.recv())
        else:
            self.disconnect_cs()
            if retries_left == 0:
                return Failure(f"Control Server seems to be off-line, abandoning ({data})")
            retries_left -= 1
            self.reconnect_cs()
            self._socket.send(pickle_string)
----

A comment above this method's retry logic states the key fact that makes all of it necessary: "we are using ZeroMQ where the connect method returns gracefully even when no server is available."

`zmq.Socket.connect()` does not fail just because nothing is listening yet. ZeroMQ handles reconnection at the transport level, transparently. A `Proxy` can be constructed, and appear to "connect" successfully, before its Control Server has even started. The real liveness test happens only the first time code tries to exchange a message, and either gets a reply or does not.

This is why the retry-and-reconnect logic lives in `send()`, not in `connect_cs()`. A timeout on `poll()` is ambiguous: it could mean the server is slow, or it could mean the server was never there. A ZeroMQ REQ socket makes this ambiguity harder to resolve directly. Once a REQ socket has sent a request, it stays in a strict alternating state until it receives a reply — it cannot simply resend on the same socket. The only sound response is to close the socket, open a fresh one, and try again. That is exactly what `disconnect_cs()`, `reconnect_cs()`, and the re-`send()` call do here.

`REQUEST_RETRIES = 0` is the module default, and it is worth stating plainly: by default, `send()` does not retry at all. It makes one attempt, and a timeout becomes an immediate `Failure`. Retrying is opt-in, per call (`send(data, retries=2)`). This keeps the default predictable for a caller that wants to fail fast, such as an interactive GUI that should not hang. Scripted code that expects transient network blips can still ask for retries explicitly.

==== `DynamicProxy` vs `Proxy`

_Two mechanisms for the same job, and an acknowledged bit of debt._

[source,python]
----
class DynamicProxy(BaseProxy, DynamicClientCommandMixin):
    def __init__(self, *args, **kwargs):
        super().__init__(*args, **kwargs)


# TODO (rik): remove all methods from Proxy that are also define in the BaseProxy


class Proxy(BaseProxy, ControlServerConnectionInterface): ...
----

`DynamicProxy` composes `BaseProxy` with a different mixin than `Proxy` does: `DynamicClientCommandMixin`, from `egse.mixin`. This looks like a second, parallel mechanism for building a dynamically commandable client object. It exists alongside the `load_commands()` mechanism that `Proxy` already has, covered in the next section.

The source still carries this comment: `# TODO (rik): remove all methods from Proxy that are also define in the BaseProxy`. Given who wrote it, this comment is worth taking at face value. It acknowledges that `Proxy` built up some duplication with `BaseProxy` over time. Methods such as `get_monitoring_port`, `get_commanding_port`, and `get_service_port` are defined on `BaseProxy`, and `Proxy` inherits them without needing to redeclare anything — but the comment suggests this was not always tidy in the past.

The Pitfalls appendix flags this as *P-008*: confirm the actual relationship between `DynamicProxy` and `Proxy`, then either consolidate them or document why both exist. This is exactly the kind of question worth a deliberate decision before a handover. A successor should not have to reverse-engineer the difference between two classes that both claim to be "the dynamic one."

==== `load_commands()`

_A Proxy that grows its own interface at runtime._

[source,python]
----
def _request_commands(self):
    response = self.send("send_commands")
    self._commands = response


def _add_commands(self):
    for key in self._commands:
        if hasattr(self, key):
            attribute = getattr(self, key)
            if isinstance(attribute, types.MethodType) and not hasattr(attribute, "__dynamic_interface"):
                self._logger.warning(f"... already has an attribute '{key}', not overwriting.")
                continue
        command = self._commands[key]
        new_method = MethodType(command.client_call, self)
        new_method = set_docstring(new_method, command)
        setattr(self, key, new_method)
----

This mechanism makes `hexapod_proxy.homing()` work, even though no `homing` method is ever written by hand in `Proxy` or its subclasses. On construction, once the ping handshake succeeds, the `Proxy` asks its Control Server for its full command dictionary, with `send("send_commands")`. The server side of this exchange is the device protocol's command registry, which is out of scope for this chapter. What comes back is a dictionary of `Command` objects — covered later, in the chapter on `egse/command.py`.

For every command name not already claimed by something else on the instance, `Proxy` binds that command's `client_call` as a genuine bound method on `self`, using `types.MethodType`. From the calling code's perspective, a "real" method and one of these dynamically attached methods look identical. That is the whole point. It is also why a device-specific `Proxy` subclass can stay almost empty across the codebase: most of its public interface does not exist as written Python at all. It gets populated at `+__init__+` time, from whatever the connected Control Server reports it supports.

*The collision guard is the one part of this worth reading closely.* If the `Proxy` already has an attribute with the given name, that attribute is overwritten only if it is not already a method carrying the `+__dynamic_interface+` marker described above. This protects two kinds of methods from a same-named device command: a connection-management method like `connect_cs`, and a regular Python method a subclass author defined without the marker. In the second case, `Proxy` logs a warning instead of silently overwriting the method. This is the practical payoff of the `ControlServerConnectionInterface`/`@dynamic_interface` split described earlier in this chapter. That split does not exist to enable the connection lifecycle of `Proxy` — it exists specifically to survive contact with `_add_commands()`.

=== `self.service_id` vs `self._service_id`

_A real, confirmed bug._

[source,python]
----
# in ControlServer.__init__:
self.service_id: str | None = None
"""The service ID of this Control Server, as registered in the Service Registry."""
----

[source,python]
----
# in ControlServer.register_service:
self._service_id = self.registry.register(...)
...
if self._service_id:
    self.registry.start_heartbeat()
----

[source,python]
----
# in ControlServer.deregister_service:
if self._service_id:
    self.registry.stop_heartbeat()
    self.registry.deregister()
----

Read this pair of code blocks closely. `+__init__+` declares and documents a public attribute, `self.service_id`, with no leading underscore. Its docstring describes it plainly: "The service ID of this Control Server, as registered in the Service Registry."

`register_service()` is the only place that assigns a value after a successful registration. But it sets `self._service_id`, with a leading underscore — a different attribute, never declared in `+__init__+` at all. `deregister_service()`, and the checks inside `register_service()`, all consistently read `self._service_id`. The internal logic is self-consistent. But the publicly documented `self.service_id` attribute is never updated by anything. It stays `None` for the entire life of the object, even after a fully successful registration.

This finding did not rest on a read-through alone. The same pattern — a service ID stored after registration — recurs across several server classes in `cgse-core`, so each one was checked:

----
egse/registry/service.py:   self.service_id = await self.registry_client.register(...)
egse/metricshub/server.py:  self.service_id = await self.registry_client.register(...)
egse/notifyhub/server.py:   self.service_id = await self.registry_client.register(...)
egse/control.py:            self._service_id = self.registry.register(...)   # <- the odd one out
----

Every sibling server class in the package assigns the public name, `self.service_id`: the registry service base, the metrics hub server, and the notify hub server. `ControlServer` is the only one that uses `self._service_id`. This consistency across three other classes makes it very likely that `self.service_id` was the intended name here too. The leading underscore in `control.py` looks like a copy-paste-era typo, one that nothing reading the public name has ever caught.

The practical consequence: any code that reads `control_server.service_id`, expecting the registered ID, always gets `None`. This happens silently, even after registration succeeds and the heartbeat is running. Only code that happens to know the undocumented `_service_id` name gets the real value.

The appendix logs this as *P-006*, and flags it as the single highest-value fix to come out of this chapter. The fix itself is one line: rename `_service_id` to `service_id` in `register_service()`. But it deserves a deliberate look at every call site across the monorepo first. A bug that is silently always `None` is exactly the kind that other code may have already, unknowingly, worked around.

=== What carries forward

_Findings, an open question, and what's next._

This chapter produced three evidence-checked findings, and one open question that needs a deliberate decision:

* *P-006* — the `service_id` mismatch, confirmed by checking three sibling classes.
* *P-007* — the self-flagged PUB-in-poller FIXME, formalized rather than silently fixed.

None of these findings tell you, directly, how to search for this class of bug in general. That method stays implicit in how they were found: read closely, then verify against siblings. That method is the real takeaway for whoever inherits this codebase. When one name sits this close to another name doing the same job elsewhere, five minutes with `grep` is worth it before trusting either one.
